# Release 1.0 audit: 6 focused beads bug cluster (sdplab-62q, vj4, 1h9, ond, 9ty, dtv)

Scope: read-only review of `internal/index/*` paths (`builder.go`, `parser.go`, `store.go`, `types.go`) only.
No unrelated codepaths were evaluated.

## Per-bug verdicts

### 1) sdplab-62q — Refresh chunk re-insertion loses edges; SourceID/TargetID become zero
**Verdict: FALSE**

**Evidence**
- `internal/index/builder.go:resolveAndInsertEdges` (line ~616): edges are not inserted from parser-returned `[]Edge`; they are built from `[]SymbolicEdge` and resolved through symbol-to-ID maps before write:
  - map build: `symbolIDMap, err := b.store.BuildSymbolIDMap(ctx)` around line ~616.
  - source/target IDs are resolved explicitly: `srcID := symbolIDMap[edge.SourceSymbol]`, `dstID := symbolIDMap[edge.TargetSymbol]` around lines ~647–666.
  - insertion only happens when both IDs are non-empty (`if !srcFound || !dstFound { continue }`).
- `internal/index/builder.go:extractSymbolicEdges` returns only symbolic edges (source/target symbols, file path references), not ID-resolved edges (line ~764 onward).

**Recommended fix direction**
No functional fix for this bug is needed for current behavior. If zero-ID edges appear, add an assertion in `resolveAndInsertEdges` that logs/records unresolved symbolic edges so missing symbols are visible instead of being silently dropped.

---

### 2) sdplab-vj4 — ColdBuild/Refresh lacks transaction wrapping; interrupted build leaves partial index state
**Verdict: PARTIALLY TRUE**

**Evidence**
- `internal/index/builder.go:ColdBuild` opens a transaction for chunk/file operations (`store.Begin`, `Commit`) and then does caller/edge repair plus metadata writes outside that transaction:
  - tx block and commit: lines ~59–64 and ~175–178.
  - `resolveAndInsertEdges(ctx,...)` and `SetMeta(...)` calls occur after commit, lines ~187 and ~190–217.
- `internal/index/builder.go:Refresh` similarly mutates many store tables inside tx and commits at line ~548, then performs symbolic edge repair and metadata writes outside tx at ~552–593.

**Recommended fix direction**
Move edge repair and all metadata writes under the same transaction scope as chunk/filetable updates, or split into a clear two-phase approach with explicit rollback/marking when post-tx steps fail.

---

### 3) sdplab-1h9 — ColdBuild edges silently discarded; parser never populates SourceID/TargetID, all edges have zero IDs
**Verdict: PARTIALLY TRUE**

**Evidence**
- Parser edge return value exists but is never populated:
  - `internal/index/parser.go:parseGo` returns `chunks, edges, nil` where `edges` is never filled (return value remains nil/zero IDs).
  - `internal/index/parser.go:parsePython`, `parseTypeScript`, `parseJava`, `parseRust`, `parseRuby`, `parseCFamily` all return `chunks, nil, nil`.
- `internal/index/builder.go:ColdBuild` and `internal/index/builder.go:Refresh` ignore parser edges from `ParseFile` and instead build symbolic edges separately via `extractSymbolicEdges`.

**Recommended fix direction**
Either (a) remove the unused parsed-edge return path from `ParseFile` and `ParseFile` callers to avoid confusion, or (b) consistently populate and consume ID-less edges through a single explicit pipeline so “parser edge” behavior is no longer misleading.

---

### 4) sdplab-ond — Edge insertion dead code (`edge.SourceID > 0` always false because parser doesn't populate IDs)
**Verdict: FALSE**

**Evidence**
- No `edge.SourceID > 0` guard was found in current ColdBuild/Refresh edge write paths.
- Edge insertion is performed from symbolic edges (`SymbolicEdge`) in `internal/index/builder.go:resolveAndInsertEdges` and never relies on parser edge IDs.

**Recommended fix direction**
No codefix for this exact claim. Add a short comment near parser signatures documenting that parser-returned `[]Edge` is intentionally not the primary edge source, or remove that value from the parser interface if dead.

---

### 5) sdplab-9ty — Silently swallowed store errors in ColdBuild/Refresh metadata writes
**Verdict: PARTIALLY TRUE**

**Evidence**
- `internal/index/builder.go:ColdBuild` metadata writes are checked and errors are appended to `result.Errors`, but execution continues:
  - lines ~190–217 (`SetMeta` calls and `append(fmt.Errorf(...))`).
- `internal/index/builder.go:Refresh` does the same for metadata writes (~585–593), appending failures to `result.Errors` but still returning `nil` error to caller unless callers treat `result.Errors` as fatal.

**Recommended fix direction**
Decide on a failure policy: either keep build non-fatal but return `errors.Join(result.Errors...)` (or equivalent) as the function error, or promote metadata writes to hard failures to avoid silently accepting incomplete index metadata.

---

### 6) sdplab-dtv — ColdBuild silently swallows chunk insert + edge insert errors, producing wrong `TotalChunks`/`TotalEdges`
**Verdict: PARTIALLY TRUE**

**Evidence**
- `internal/index/builder.go:ColdBuild`:
  - chunk insertion failures are appended to `result.Errors` and processing continues, while counters are only incremented on success (`result.TotalChunks++` around chunk loop lines ~120+).
  - edge repair/count returns are additive from `resolveAndInsertEdges`, so total edge count is based on inserts that happened in that final pass, not necessarily all logically expected inserts.
- `internal/index/builder.go:Refresh` updates `result.TotalChunks` / `result.TotalEdges` from store state after mutation (around ~585–593), not from parser-derived intended graph cardinality; failed inserts before commit can still bias observed counts.

**Recommended fix direction**
Track and expose structured failure counts separately from actual stored totals, and fail build when hard thresholds are crossed (e.g., any insert error or high unresolved-edge rate) instead of only continuing with partial metrics.

---

## Aggregate observations
- All six claims cluster around two design issues:
  1. **Edge model mismatch:** symbolic edge resolution is the effective model, while parsed edge IDs are vestigial/unconsumed; this causes some “zero-ID” bug claims to be false but also causes ambiguity in future maintenance.
  2. **Transaction boundary mismatch:** edge regeneration and metadata writes happen after commit in both ColdBuild and Refresh, creating windows for partially persisted state and harder incident recovery.
- Error handling is intentionally tolerant: build continues after many store/insert errors and records them in `result.Errors`. That policy is useful for resilience but produces “silent” behavior unless consumers treat `result.Errors` as fatal.

## Findings
- [P2] `internal/index/builder.go:ColdBuild` :: Metadata writes and symbolic edge repairs execute outside the tx that writes chunks/metadata source tables, so an interruption can leave non-atomic build state.
- [P2] `internal/index/builder.go:Refresh` :: Same pattern as ColdBuild: graph repair and `SetMeta(...)` happen after commit, creating partially persisted states on failure.
- [P2] `internal/index/parser.go:ParseFile/parse*` :: Parser returns `[]Edge` and error triple, but edge IDs are not populated and these return values are ignored by callers, which is a maintainability risk.
- [P3] `internal/index/builder.go:ColdBuild`, `internal/index/builder.go:Refresh` :: Store/metadata errors are collected but not treated as fatal by default; `TotalChunks/TotalEdges` can be interpreted as partial counts without explicit failure signal.
