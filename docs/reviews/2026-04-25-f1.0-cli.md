### Exit-code outliers
- No single contract for what constitutes failure versus hard failure.
- Codes `2` and `3` appear in at least 6 binaries with no uniform meaning (`sdp`/`sdp-control` usage vs `sdp-orchestrate` checkpoint-corrupt `3`).
- `sdp-gh-findings-sync` violates non-error exit contract by not exiting non-zero when sync tasks fail internally.

## 4) Help text consistency

Observed shapes:
- `default Usage of <binary>` from Go flag package: 11 binaries.
- Manual usage blocks with custom prose/examples: 7 binaries.
- Root `sdp` and `sdp-control` have manual dispatch text and no consistent top-level `--help` policy.
- Custom blocks vary in style: emojis, `USAGE` casing, spacing, command grammar, and punctuation are inconsistent.
- Exit-on-help is inconsistent: some subcommands exit `0`, some exit `1`/`2` with only missing required subcommand.

Examples by binary:
- `sdp` uses custom `usage: ... [subcommand] [flags]` plus long list, but no top-level `--help` entrypoint and no usage for missing required arguments.
- `sdp-beads-bridge` and `sdp-strataudit` expose command trees but return non-zero for help requests.
- `sdp-up` references `sdp up` while binary is `sdp-up`, causing documentation mismatch in help text.
- `sdp-up` help text omits full flag list for JSON/config/output consistency and omits failure preconditions.

## 5) Subcommand convention

- No binary under this scope uses Cobra.
- Current command surface mixes:
  - Deeply nested custom dispatch (`sdp`, `sdp-control`, `sdp-dispatch`, `sdp-beads-bridge`, `sdp-harness`, `sdp-strataudit`).
  - Pure-flag mode with no subcommands (`sdp-a2a`, `sdp-ci-loop`, `sdp-orchestrate-daemon`, etc.).
- `sdp-control` uses legacy hyphenated names (`card-create`, `board-build`) that differ from canonical `sdp` verb/noun style and are explicitly marked deprecated.
- `sdp-dispatch` mutates `os.Args` (`os.Args = os.Args[1:]`) before dispatch; this is fragile and non-local and can break wrappers/tests.
- `sdp-orchestrate` and `sdp-a2a` lack discoverability from help for action names beyond flags and rely on internal docs/README.

## 6) Error format and machine-readability

- No shared machine-error schema across binaries.
- Prefixes are inconsistent (`error:`, `Error:`, `ERROR:`, `WARN:`, `SCOPE VIOLATION:`).
- `--json` does not guarantee JSON-only output; several binaries still print informational/log/usage text before/after JSON output.
- `sdp-omc-guard` is the only binary with structured success payload (plain `GuardResult`), but still emits mixed stderr strings on error paths.
- `sdp-control` and `sdp` emit many short-form command-specific strings that are hard to parse and version-control.

## 7) Output format / `--json` piping support

- Binary-level JSON support is inconsistent:
  - Consistent structured output: `sdp-doc-sync`, `sdp-healthcheck`, `sdp-orchestrate`, `sdp-protocol-check`, `sdp-ready`, `sdp-session-audit`.
  - Partial/subcommand-level JSON: `sdp-beads-bridge`, `sdp-dispatch`, `sdp-omc-guard` (success-only envelope).
  - No JSON mode: majority of binaries (e.g., `sdp-a2a`, `sdp-ci-loop`, `sdp-gh-findings-sync`, `sdp-up`, `sdp-ws-verdict-validate`, etc.).
- `sdp-ws-verdict-validate` cannot emit machine/help friendly output under `--help` because the argument parser is positional-only.
- Some binaries support `--format json`, but no global `--json` alias (e.g., `sdp-protocol-check`, `sdp-doc-sync` partly).

## 8) Configuration source precedence (`env`, `.sdp/config.yml`, flags`)

- `.sdp/config.yml` is not a recognized input on any inspected command.
- Most binaries have ad-hoc `--project-root` and no config file support.
- Explicit env-driven config is sporadic: `sdp-harness` (`SDP_DATA_DIR`, `SDP_HARNESS_BD_PATH`), `sdp-mcp` (`SDP_LOG_LEVEL`), `sdp-omc-guard` (`CWD` fallback), `sdp-up` uses only cwd traversal.
- No global policy exists for precedence (env > config-file > flags) in the CLI family.
- `sdp-strataudit` is the only command with a first-class config-file flag (`--config`).

## 9) Recommended canonicalization (targeting F137)

1. Introduce a shared CLI foundation in `cmd/internal/cli` with standard surface: `--help`, `--version`, `--json`, `--dry-run`, `--config`, `--quiet`, `--verbose` defaults and common usage template.
2. Normalize subcommand architecture: migrate to either `cobra` for all binaries or a single local manual dispatch framework with identical exit/help conventions.
3. Standardize non-zero semantics: `0` success, `1` user/runtime error, `2` policy failure, `3` corrupt-state and only where explicitly documented.
4. Replace ad-hoc error strings with machine-parseable envelopes in `--json` mode; provide deterministic key names and explicit error codes (`err_code`, `command`, `field`).
5. Add config precedence policy shared by all binaries: `$SDP_*` envs + `.sdp/config.yml` + explicit flags + explicit precedence docs.
6. Gate track progress for `sdplab-pg7o` by requiring every reviewed binary to pass a CLI contract test suite (help, version, json, exit matrix, help tone).

## 10) Findings list

- `sdp-ws-verdict-validate` help/CLI behavior is a contract breaker: `--help` is parsed as a positional project root and returns schema read error.
- `sdp` lacks a `--help` flag and returns usage errors (`2`) instead of explicit help command handling.
- `sdp-control` is deprecated but still shipped without migration wrapper parity and duplicates `sdp` command surface.
- No binaries in this review use Cobra, so subcommand behavior is bespoke in every executable.
- `--quiet` and `--verbose` are absent in all 23 binaries, preventing parity with release expectations.
- `--version` exists only in `sdp-mcp`.
- `--config` exists only in `sdp-strataudit`.
- `sdp-evidence` and `sdp-ws-verdict-validate` provide no machine flags and no error schema.
- `sdp-beads-bridge` and `sdp-evidence` return non-zero for help context with no actionable help/error framing.
- `sdp-strataudit` returns usage exit for `--help` equivalently (missing subcommand semantics).
- `sdp-doc-sync`, `sdp-healthcheck`, `sdp-orchestrate`, `sdp-protocol-check`, `sdp-ready`, `sdp-session-audit` support JSON, but their help text does not explicitly document machine-readability guarantees.
- `sdp-doc-sync` and `sdp-protocol-check` use `--json` aliases while also exposing `--format json`, creating inconsistent user memory model.
- `sdp-gh-findings-sync` prints failures yet exits `0` in many failure paths.
- `sdp-orchestrate` uses exit code `3` (`ExitCorrupted`) without top-level user contract or explicit man page.
- `sdp-ci-loop` uses exit class `2` for both max-iteration and several escalations; semantics are not documented.
- `sdp-control`/`sdp`/`sdp-strataudit` mix exit codes for usage vs execution with no consistent boundary.
- `sdp-dispatch` mutates `os.Args` in `main`, an anti-pattern for wrapped command execution and tests.
- `sdp-dispatch` uses `flag.ExitOnError` in subcommands while `sdp-dispatch/main.go` maps unknown commands to exit `2`, creating mixed behavior inside one binary.
- `sdp-control` emits lowercase warning lines, mixed with uppercase severity words, with no schema.
- `sdp-a2a` has no validation/help contract and exits only on server errors.
- `sdp-ci-loop` does not expose help examples or JSON output schema.
- `sdp-up` help usage text shows `sdp up` (not `sdp-up`) and misses discoverability of `--project-root`-equivalent behavior.
- `sdp-orchestrate-daemon` has no `--config`/`--json` or `--help` examples and minimal operational output guidance.
- `sdp-omc-guard` does not include explicit machine-readable errors despite being automation infrastructure and returning multiple non-zero semantics.
- `sdp-healthcheck` prints icons and plain text in success mode, no dedicated error envelope in success/failure mix.
- `sdp-mcp` logs via stdlib logger by default; log format may inject noise into consumers if machine parsing is expected.
- `sdp-ready`/`sdp-protocol-check`/`sdp-doc-sync` use cache/result codes (`2`) to signal logical failures that may be indistinguishable from execution failures without parsing payloads.
- `sdp` has many commands that are not exposed in top-level command docs while many `cmd/sdp/main.go` modes exist only as secondary docs.
- Root subcommand `sdp` has no documented `--version`; no binary exposes full version metadata except `sdp-mcp`.
- No binary validates or echoes effective config precedence to support reproducibility (env vs config vs flag).
- No global command-line policy for output truncation, color toggles, quiet mode, or machine mode for all binaries.
- Top-level `sdp` and `sdp-control` route commands but expose inconsistent naming vs modern subcommands (`card-create` vs `card create`).
- `sdp-beads-bridge` has `--vars` and `--format` options in subcommands but no shared common `--project-root`/`--config` semantics.
- `sdp-strataudit` and `sdp-up` have custom usage blocks that deviate from standard section headers and argument ordering.
- `sdp-ws-verdict-validate` has no tests on its CLI behavior and is the only binary without a flag parser and standard conventions.
- `sdp-a2a` is long-running server with no shutdown flags, no readiness checks, and no output mode contract.
- `sdp-session-audit` uses all-caps `ERROR:` on validation failures only, diverging from project style.
- Several binaries print `fmt.Println`/`fmt.Printf` errors directly; only some use `fmt.Fprintf(os.Stderr, ...)`, making stream redirection brittle.
- No common help banner includes exit guarantees per command.
- No shared schema check exists for machine-readable outputs, so downstream tooling must parse 20+ variants.
- No CLI-level deprecation policy for `sdp-control` usage; it still prints warnings but remains operationally mutable.
- `sdp-control` and `sdp` duplicate command logic paths instead of shared command registration.
- `sdp-doc-sync` uses default `flag` package and may exit on unknown flags without JSON-safe envelopes.
- `sdp-orchestrate` has many non-trivial branches with direct `os.Exit`, making unit/integration composition difficult.
- `sdp-protocol-check` and `sdp-ready` expose output mode knobs but no common `--output` semantics.
- `sdp-gh-findings-sync` uses `--output` string and prints sync progress to stdout (not structured) while claiming machine integration intent.
- `sdp-beads-bridge` emits emoji-heavy text (`📋`) that complicates deterministic snapshots.
- `sdp-healthcheck` icon set (`✓`, `✗`, `!`) is not output-mode neutral.
- `sdp-eval` reports pass/fail summary in plain text and cannot emit JSON.
- `sdp-guard` overloads severity exits (`0`,`1`,`2`) without machine mapping or docs.
- `sdp-orchestrate` and `sdp-ci-loop` both include internal retry/escalation states with no machine schema for CI automation.
- No cross-binary convention for `--dry-run` effect (global vs scoped, and whether output is emitted without mutation).
