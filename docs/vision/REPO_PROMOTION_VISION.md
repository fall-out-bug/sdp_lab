# Repo Promotion Vision

Status: active
Updated: 2026-03-03
Scope: OSS-first promotion strategy for SDP trust layer

## 1. Positioning

Primary message:

SDP is the trust layer for AI software delivery: it adds verifiable provenance and evidence to agent-driven development.

Supporting message pillars:

- Not another orchestrator clone: focus on proof and governance
- Standards-based trust (in-toto, OPA, Sigstore)
- Portable across runtimes, OpenCode-first in execution

## 2. Audience segments

- Builders running AI coding assistants in CI
- Staff+ engineers owning SDLC governance and release quality
- DevEx/tooling teams evaluating agent reliability controls

## 3. Promotion channels (execution-first)

Weekly:

- GitHub release notes and concise changelog narrative
- One technical post (blog or long-form note)
- One community distribution action (awesome lists, Discord/Slack, X/LinkedIn)

Monthly:

- One end-to-end demo walkthrough (video or scripted demo repo)
- One ecosystem collaboration touchpoint (upstream issue/PR or integration note)

Quarterly:

- One major narrative launch (state-of-the-project report)

## 4. Content architecture

Canonical outward reading path:

1. `docs/MANIFESTO.md`
2. `docs/vision/SDP_LAYERED_VISION.md`
3. `docs/roadmap/ROADMAP.md`
4. `docs/getting-started.md`

Rule: all other promo/positioning docs must support these four, not contradict them.

## 5. Weekly promotion checklist

- Release one finished feature with usage guidance
- Publish one evidence-backed update post
- Publish one comparison insight vs market alternatives
- Capture feedback and convert into one backlog decision

## 6. Metrics

- GitHub stars/watch growth trend
- External issue/discussion conversion rate
- Docs-to-install conversion proxy
- Number of third-party references (awesome lists, blogs, talks)
- Repeat external users for released capabilities

## 7. Risks and controls

Risk: over-fragmented narrative across too many documents.

Control:

- quarterly archive/supersede pass for stale positioning docs
- keep one canonical launch narrative and one canonical roadmap narrative

Risk: promoting before feature readiness.

Control:

- promotion only for features that satisfy weekly definition of done
