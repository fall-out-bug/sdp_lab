# Давай проревьюим по сути основные промпты протокола

Разберём по сути: что эти три скилла делают правильно, а где архитектурные дырки.

## @oneshot (SKILL.md)

**Что хорошо**

- Чёткий контракт: LLM не рулит процессом, только выполняет @build/@review, а внешняя CLI `sdp-orchestrate` держит стейт.[^1]
- Минимум правил, нет «никогда/всегда» магии, нет автолоопов.[^1]
- Есть явное «done» состояние с коротким выводом, что уменьшает болтовню и облегчает автоматизацию.[^1]

**Где дыры**

- Дублирование advance: в правиле 2 ты уже вызываешь `--advance`, и правило 3 ещё раз говорит «после каждого фейза — advance». Высокий риск двойного шага, особенно если LLM неидеально различит случаи.[^1]
- Не зафиксирован формат JSON из `--next-action`: без схемы агент будет парсить как попало, тяжело проверять.[^1]
- Нет ограничения на изменение scope: нет явного запрета трогать не входящие в workstream файлы.[^1]

**Что бы я усилил**

- Развести ответственность:
    - Правило 2: «для build/review делай ровно X и не вызывай advance руками, если CLI уже вызвана в шаге».
    - Или наоборот: убрать advance из шага 2 и оставить только правило 3 как единый способ перехода.
- Добавить мини‑схему `--next-action` (action, ws_id, phase, allowed_commands) в явном текстовом описании.
- Вставить жёсткий запрет: «изменяй только файлы из Scope Files текущего workstream, ничего вне этого списка не трогать».


## @feature (SKILL-1.md)

**Что хорошо**

- Очень конкретный pipeline: roadmap → workstreams → beads, с командами `rg`, путями, форматами файлов. Это близко к Stripe‑стилю «операционная конкретика».[^2]
- Моды `--auto/--quick/default` и явные гейты (overlap report, вопросы интервью) — хорошо управляют глубиной.[^2]
- Workstream file format задаёт чёткий контракт: Goal, Scope Files, Dependencies, AC.[^2]

**Где дыры**

- Явно хардкожен Go/инфраструктура проекта (go build/go test, структура docs/...). Это уже частично конфликтует с твоим vision «language‑agnostic protocol».[^3][^2]
- Много скрытой логики в фразах типа «Auto-trigger when @idea output has user-facing keywords» — это эвристика без границ, её тяжело стабилизировать.[^2]
- Нет связи с evidence: скилл генерит важные артефакты (workstreams, beads mapping), но не описано, как это потом попадает в SDP‑evidence/attestation.[^4][^2]

**Что бы я усилил**

- Вынести Go‑специфику в AGENTS.md: в AC вместо `go build/test` — «Run quality gates (see AGENTS.md)», а сами команды уже описать в конфиге, как ты планируешь.[^3]
- Сформулировать чёткий детерминированный критерий вызова @ux (например, флаг `--ux`, а не NLP‑эвристика по словам). Эвристику можно оставить как «подсказку», но не как правило.
- Явно описать, какие evidence/мэппинги обязан создать скилл: например, «каждый созданный workstream должен иметь строку в .beads-sdp-mapping.jsonl, и это проверяется в Step D».


## @vision (SKILL-2.md)

**Что хорошо**

- Правильный уровень абстракции: это стратегический скилл, цели ясны — vision, PRD, roadmap, feature‑drafts.[^5]
- Есть фиксация, что он работает на «моментах изменения траектории» (initial, quarterly, pivot, new market).[^5]

**Где дыры**

- «7 Expert Analysis» описан одной строкой, без формата выхода. Риск: превратится в очередное расплывчатое эссе.[^5]
- PRD Mode переоценён: автодетект типа проекта, диаграммы из `@prd`‑аннотаций — это довольно сложное поведение без описанного контракта и ограничений.[^5]
- Опять нет явной схемы артефактов: какие разделы в PRODUCT_VISION.md, какие поля в PRD, как связаны фичи из roadmap с `docs/drafts/feature-*.md`.[^5]

**Что бы я усилил**

- Для «7 Expert Analysis» задать табличный формат: по каждому эксперту — 3 bullets insights, 2–3 риски, 1 рекомендация.
- Описать явный шаблон PRD (разделы, лимиты, что обязано быть заполнено).
- Жёстко ограничить автоматику:
    - детект типа проекта — best‑effort плюс обязан явно писать confidence;
    - генерация диаграмм — как опциональный шаг, который может быть пропущен, если нет аннотаций.

***

Если коротко: структура у тебя очень сильная, основная проблема — остаточные «магические» места (двойные advance, эвристики, хардкод стека, неформализованные «эксперты»). Следующий шаг логичный: для каждого из трёх скиллов прописать минимальные схемы (форматы JSON, шаблоны markdown, детерминированные триггеры) и выпилить из описания всё, что не может быть проверено или воспроизведено.
