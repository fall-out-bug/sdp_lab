# Давай еще порцию отревьюим

С этими четырьмя ты уже очень близко к нормальному протоколу. Давай по сути, без поглаживаний.

***

## @build (SKILL-3)

**Сильное:**

- Жёсткий инвариант «ONE workstream and STOP» — ровно то, чего не хватало раньше.[^1]
- Разделение: guard/ scope в CLI, evidence lifecycle тоже вынесен — промпт не тащит на себе весь ад.[^1]
- Чёткий контракт ws-verdict (ws_id, feature_id, verdict, commit, quality_gates, ac_evidence[]) — это уже почти evidence‑schema.[^1]

**Дыры:**

- `CHECK EXISTING CODE FIRST` никак не формализован: что считать достаточной проверкой? Сейчас это «попросили — может сделаю, может нет».[^1]
- Git safety-блок в skill — это скорее doc для людей, чем реальный шаг для LLM; большая часть этого должна жить в CLI/скрипте, а не в голове модели.[^1]
- TDD‑цикл описан в виде ролей, но не в виде выхода: для orchestrator’а важно не «RED→GREEN→REFACTOR», а какой артефакт/лог останется по завершении.[^1]

**Что бы я поменял:**

- «CHECK EXISTING CODE FIRST» превратить в обязательный шаг с ожидаемым выходом: короткий «Existing Work Summary» (файл/функция/risks) в ws‑verdict.[^1]
- Git‑проверки — максимально выпихнуть в `sdp guard activate`/CLI, в skill оставить только «запусти CLI и не пытайся переписать команду руками».[^1]
- Для subagent‑ролей задать жёсткий output‑формат (JSON‑фрагменты для implementer/spec/quality), чтобы их можно было мёрджить и проверять автоматически.

***

## @review (SKILL-6)

**Сильное:**

- Нормальная постановка: CLI (`sdp quality all`) + 7 специализированных субагентов, PASS/FAIL по P0/P1, вывод в `.sdp/review_verdict.json`.[^2]
- Есть единый шаблон задачи для субагентов и единый формат verdict, это хорошо режет болтовню.[^2]

**Дыры:**

- «Spawn 7 subagents IN PARALLEL. DO NOT skip» — типичное желательное поведение без enforce: модель легко «забудет» 1–2 роли.[^2]
- В описание verdict’а нет явной схемы для поля `reviewers` (что там: по ролям? массив? структура?), это плохо для downstream‑инструментов.[^2]
- PromptOps‑проверки перечислены текстом (language‑agnostic, no phantom CLI, skill size ≤200 LOC), но ни формат отчёта, ни критерии PASS/FAIL не заданы жёстко.[^2]

**Что бы я поменял:**

- Явно перечислить 7 ролей в expected‑списке `reviewers` в verdict‑JSON и указать, что APPROVED возможно только если для каждой роли есть запись и verdict=PASS.[^2]
- Формализовать для PromptOps и Docs хотя бы минимальную таблицу output’а: `check_id / status / note`, чтобы потом reality/protocol-consistency могли это читать.[^3][^2]
- В шаблон задачи субагента добавить: «Если находок нет, всё равно явно выводи `FINDINGS_CREATED: (none)` и `PASS`», чтобы не было двусмысленных пустых ответов.[^2]

## @deploy (SKILL-4)

**Сильное:**

- Чёткие pre-flight условия: APPROVED verdict, нет P0/P1, quality gates пройдены. Это хороший gate перед продом.[^4]
- Разделение PR vs Release, явный quick‑reference, troubleshooting.[^4]

**Дыры:**

- Жёсткий tie-in к `master` и `go.mod` — это снова language/branch‑model leakage; для протокола, который ты хочешь реплицировать «в каждый дом», это слишком частный случай.[^5][^4]
- Много «голых» CLI‑команд (`gh pr create`, ручное bump‑ление версии). Это больше operational‑runbook, чем LLM‑skill: часть этого должна жить в make/CLI.[^4]
- Нет связи с evidence: деплой — это ключевое событие, но skill не говорит, как отмечать выпуск в SDP‑evidence (release‑attestation, mapping PR↔feature).[^6][^4]

**Что бы я поменял:**

- Вынести branch‑schema и `gh`‑команды в AGENTS.md как «how», а в skill оставить только «WHAT» (создать PR мастер←feature, создать релиз на main branch).[^5][^4]
- Добавить обязательный шаг «записать release‑event» (feature, PR url, tag, timestamp) в отдельный evidence‑файл.[^6][^4]
- Чётко оговорить, что, если проект не Go, шаг с `go.mod`/CHANGELOG.md может быть no-op/альтернативой (reference на AGENTS‑конфиг).

## @idea (SKILL-5)

**Сильное:**

- Прямо хорошая инженерная постановка интервью: прогрессивное раскрытие, 3‑вопросные циклы, TMI detection, `--quiet` для опытных.[^7]
- Есть чёткое ожидание артефактов: Beads‑task, `docs/intent/{task_id}.json`, question‑count в метаданных.[^7]

**Дыры:**

- «Минимум 12, максимум 27 вопросов» — это статистика, не контракт. Модель может выдать 9 вопросов и считать, что всё ок; проверять это сложно, если не зафиксировать формат лога.[^7]
- TMI detection завязана на ключевые слова и >500 символов — это хрупкая эвристика, и она описана словами, а не как обязательный check.[^7]
- Intent‑JSON не имеет описанной схемы: какие поля обязательны (problem, users, success, risks, constraints и т.п.).[^7]

**Что бы я поменял:**

- Явно требовать лог интервью в `docs/intent/{task_id}.json` (вложенный массив вопросов/ответов) и на его основе считать вопрос‑count.[^7]
- Формализовать schema intent‑файла: обязательные поля `context`, `problem`, `users`, `goals`, `non_goals`, `tech`, `risks`, `metrics`, плюс `question_count`.[^7]
- TMI detection: перевести в правило «если initial prompt > N символов — сначала коротко резюмируй и предложи три опции (доп.вопросы / сразу @design / --quiet)», с явным форматом вывода этого решения.

***

Если суммировать: у тебя уже не «промпты», а зачатки реально жёстко определённого протокола. Главный общий недочёт по этой порции — много вещей сформулированы как «разумные пожелания» и эвристики, а не как проверяемые контракты (структура JSON, минимальные поля, явно перечисленные роли, связь с evidence). Следующий шаг — именно это: в каждый skill добавить минимальные схемы и инварианты, чтобы любой будущий «Stripe‑уровень» мог на них полагаться, а не надеяться «что агент умный».
