# 00-167-02: F167 Gateway Sanitation And Audit

Feature: F167 (sdplab-xe5c)
Phase: Pilot Evidence & Spec Quality
Status: Backlog

## Goal

Add the gateway-side sanitation and audit layer required by the security verdict
gate. Model-bound security-review prompts must redact secrets and high-confidence
PII before provider egress and record evidence that says what was clean,
redacted, or blocked without storing sensitive values.

## Acceptance Criteria

- [ ] Security-review prompt assembly uses a sanitizer before any provider call.
- [ ] Sanitizer covers known secret/token patterns, private keys, connection strings, auth headers, and high-confidence PII.
- [ ] Audit evidence records class/count/status only; it never stores raw secret, token, or PII values.
- [ ] High-confidence detection is defined as deterministic matches from existing secret filter patterns plus explicit auth-header/private-key/connection-string patterns; low-confidence URL/generic entropy guesses do not block by default.
- [ ] Hashes in audit evidence use SHA-256.
- [ ] Gate can distinguish `passed_clean`, `redacted`, `blocked_before_provider`, and `sanitizer_error`.
- [ ] Tests prove provider calls receive sanitized content while evidence preserves hashes/counts.
- [ ] Tests prove high-confidence secrets can block before provider egress.
- [ ] Targeted tests pass without live provider credentials.

## Out of Scope

- Broad redaction rollout for every historical LLM call site.
- Low-confidence PII keyword blocking that would make normal code review unusable.
- External vault integration.
