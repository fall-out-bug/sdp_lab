## 4. Review tracks (parallel, codex-driven)

Each track produces:

1. A markdown report at `docs/reviews/2026-04-25-f1.0-{track}.md`.
2. A structured findings list `[P0|P1|P2|P3] <area> :: <description>`.
3. Findings ingested back as new beads issues, depending on the track parent.

| Track | Scope | Report path |
|------|------|-------------|
| R1 Skills | `prompts/skills/*.md` (41) | `docs/reviews/2026-04-25-f1.0-skills.md` |
| R2 CLI | `cmd/sdp-*` (23 binaries) | `docs/reviews/2026-04-25-f1.0-cli.md` |
| R3 Hooks | `.claude/hooks/*` + Stop hook + install scripts | `docs/reviews/2026-04-25-f1.0-hooks.md` |
| R4 Code | `cmd/`, `internal/`, key `scripts/` | `docs/reviews/2026-04-25-f1.0-code.md` |

## 5. Findings → beads ingestion contract

After each review report lands, a follow-up agent (or this orchestrator) ingests findings:

* Each `[P0|P1|P2|P3]` line in the findings list → one beads issue.
* Title: `F1.0/{track}: <description>` (truncated to ~80 chars).
* Type: `bug` if functional defect, `task` otherwise.
* Priority: from the `[Px]` tag.
* Description: includes finding context + link to the report.
* Dependency: `bd dep add <new-issue> <track-parent>` — fixes block the track's closure.

## 6. Multi-session execution model

* **Session 1 (this session)**: skeleton + dispatch reviews + ingest findings (skills/CLI/hooks/code).
* **Session 2..N**: pick up `bd ready` from review-finding issues; drive via SDP `@oneshot` / `@sweep` / `@build` per SDP protocol; close, push.
* **Session R'**: R5 docs review fires once R1–R4 are done.
* **Session D**: D1 demo build fires once R1–R5 closed.
* **Session F**: smoke + tag.

Each session ends with `scripts/beads_transport.sh export` + `git push` (per `AGENTS.md` close protocol).
